Your eval gate has a memory now.

arbiter gate tells you whether today's build regressed. What it cannot tell you, because it only ever sees one run, is that the task which just went red has been flipping every other run since March. This does.

Sign in with GitHub Read the docs

Your API keys and your agent stay in your CI. Only the verdict is posted here.

Flaky or just broken

A task that alternates between flagged and clear has an unstable signal. One that is flagged nearly every time is a regression nobody fixed. Those want different responses, so they are counted separately rather than piled into a single list of unreliable tests.

Is this actually new

Every task keeps its own row for every run, so opening one shows how it has behaved across the last fifty. Red for the fourth run running is a different conversation from red for the first time.

Where the replicates go

Cost per decision, per task. The expensive ones are usually the ones where a seed is not being threaded through properly, and that is the cheapest thing on the list to fix.

Wiring it up

Two flags on the job you already have. The gate keeps running in your CI, where your credentials already live. 

- name: eval gate
  run: |
    arbiter gate evals/suite.yaml \
      --store .arbiter/runs.sqlite \
      --publish {{ settings.base_url }} \
      --publish-token $ARBITER_HUB_TOKEN

The exit code still comes from the gate, so a regression still fails the job. Publishing is additive, and a hub that is down will not fail your build.
